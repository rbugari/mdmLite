# v0.3 Candidate Review Draft

## Objective

Prepare the next product phase after release readiness: introduce a candidate-review layer without breaking the current governed rule model.

## Why This Comes Next

The current product already governs approved operational rules well enough for a first trial. The next meaningful product step is not broader automation inside final rule tables, but a safe place to review proposed rules before promotion.

This keeps the product boundary clean:

1. detection stays separate from approval
2. suggestions stay separate from production rules
3. human review remains mandatory

## Product Goal

Allow the system to receive candidate rules from manual, file-based, or future external sources and let users review them before promotion into the existing governed entities.

## Scope

v0.3 should include:

1. candidate storage
2. candidate list and detail review experience
3. evidence and confidence visibility
4. approve, reject, and promote actions
5. audited promotion into mappings, groups, or parameters

v0.3 should not include:

1. autonomous publishing to final tables
2. full document discovery engine
3. full external analyzer orchestration
4. enterprise workflow expansion beyond what is needed for candidate review

## Conceptual Flow

1. a candidate enters the system
2. the candidate is stored with source, evidence, and confidence
3. a user reviews the candidate
4. the user rejects it or promotes it to a governed entity flow
5. promoted data enters the current operational lifecycle with audit intact

## Candidate Minimum Contract

Every candidate should minimally include:

1. `candidateType`
2. `payload`
3. `evidence`
4. `confidence`
5. `sourceKind`
6. `needsHumanReview`
7. `status`

## Candidate Status Model

Recommended initial status set:

1. detected
2. under_review
3. promoted
4. rejected
5. archived

## Review Questions

The review experience should let a user answer:

1. what is being proposed
2. what evidence supports it
3. how confident is the source
4. what entity type should it become
5. should it be rejected, held, or promoted

## Promotion Principle

Promotion should create or route data into the existing governed write model, not bypass it.

That means:

1. candidate storage is not a new production contract for downstream readers
2. final downstream consumers still read from approved active views
3. audit history must preserve the relationship between the promoted rule and its source candidate

## UX Draft

Minimum UX for v0.3:

1. candidate inbox page
2. filter by candidate type, status, source kind, and confidence
3. candidate detail panel with evidence
4. promote action with target entity confirmation
5. reject action with optional note

## Data Design Questions

These decisions should be closed before implementation:

1. whether candidate payload is normalized by type or stored as typed JSON with validation
2. how much evidence text is persisted versus referenced
3. whether promotion creates draft records or pending approval records directly
4. how candidate deduplication is handled in the first version

## Acceptance Criteria

v0.3 is ready when:

1. a candidate can be stored without touching final rule tables
2. a reviewer can inspect evidence before deciding
3. a candidate can be rejected and remain auditable
4. a promoted candidate can become a governed rule through the existing lifecycle
5. downstream technical contracts remain unchanged

## Dependency On Current Phase

This phase should start only after release readiness is closed. Otherwise the team risks mixing product design work with unresolved installability and support gaps.

## Related But Separate Initiative

The broader public-facing site for the family of products is strategically related, but it should be planned outside this repository scope. The candidate-review layer should stay focused on product capability, not portfolio presentation.
